# NixOS Architecture V2

> Исторический отчёт об итерации V2. Позднее по просьбе владельца удалены
> отдельные Nixvim packages/apps для `nix run` и переводы документации.
> Актуальная структура описана в README и architecture.md.

Дата: 12 ноября 2026. Ветка: `refactor/nixos-architecture-v2`.
База сравнения: `4083c93` — завершённая первая итерация после удаления Rust-меню.
Рабочее дерево перед началом было чистым; дополнительный checkpoint не требовался.

## 1. Архитектура до и после

`flake-parts` уже присутствовал в первой итерации. V2 сохраняет его закреплённую
версию и делает организацию outputs явной, не проводя искусственную повторную
миграцию. До изменений основная логика `perSystem` находилась в `flake.nix`,
реестр выбирал профили, а `mkHost` неявно добавлял базовый модуль.

Теперь путь чтения конфигурации следующий:

```text
flake.nix
  hosts/default.nix                 top-level NixOS и Home Manager outputs
    hosts/<name>/default.nix         база, профили, hardware и настройки машины
      configuration.nix / core/     общие системные модули
      profiles/                     workstation, development, personal
  flake/nixvim.nix                   perSystem packages и apps Nixvim
  flake/quality.nix                  perSystem formatter, devShell, checks, VM test
```

Все пути imports объявлены вручную. Каталог сам не создаёт output. Существующие
`core/`, `configs/` и `home/` сохранены: переименование в `modules/` не решало бы
отдельной задачи. Отдельные каталоги `overlays/` и `pkgs/` проекту сейчас не нужны.

## 2. Что упрощено

- Каждый хост сам выбирает базу, `workstation`, `development` и `personal`.
  `workstation` больше не подключает инструменты разработки скрыто.
- Архитектура CPU задаётся аппаратным модулем, без дублирования в реестре.
- Удалены пустые, неиспользуемые `core/dev/default.nix` и `core/hardware/default.nix`.
- Удалены неиспользуемые inputs `bundlers` и `dgop` и их недостижимые зависимости.
  Пакет `dgop` в пользовательском окружении сохранён: прямой input для него не использовался.
- В приложениях Nixvim устранено повторение описания, добавлено `meta.description`.
  Rust-меню и его установщик не возвращались.

## 3. Helpers

Удалён `mkHost` вместе с `lib/default.nix`. Он добавлял базовый модуль, повторно
задавал архитектуру и проверял согласованность двух её объявлений. Теперь реестр
использует стандартный `nixpkgs.lib.nixosSystem`, а проверки текущих хостов
проверяют фактическую архитектуру.

`mkHome` сокращён до локальной функции одного аргумента рядом с двумя standalone
outputs. Общий `x86_64-linux`, policy и внешние HM-модули остаются видимыми в
этом файле. `lib/home-modules.nix` и `lib/package-policy.nix` сохранены: они
используются как встроенным, так и standalone Home Manager и не дублируют
функции `nixpkgs.lib`.

## 4. flake-parts

Версия осталась `4524271976b625a4a605beefd893f270620fd751`. `mkFlake` явно
импортирует модуль Home Manager, `hosts/` и два файла из `flake/`.
`nixosConfigurations` и `homeConfigurations` остаются top-level;
packages/apps/devShells/checks/formatter определены через `perSystem` для
`x86_64-linux`. Источник `pkgs` — основной закреплённый Nixpkgs. Это соответствует
[разделению outputs в flake-parts](https://flake.parts/getting-started.html).

Основной Nixpkgs сохранён на `34268251cf5547d39063f2c5ea9a196246f7f3a6`,
`nixos-26.05`. Проверка lock-графа относительно базы подтвердила:

| Метрика                       |  До | После |
| ----------------------------- | --: | ----: |
| Прямые inputs                 |  17 |    15 |
| Узлы flake.lock, включая root |  61 |    55 |
| Разные полные ревизии Nixpkgs |   7 |     6 |

У всех 54 оставшихся non-root узлов совпадают метаданные и связи. Все `follows`
разрешаются, недостижимых узлов не осталось. Ни один используемый pin не обновлён.

## 5. Решение по flake.modules

Закреплённая версия flake-parts поддерживает необязательный
`flakeModules.modules`; новый input для него не нужен. Но проект не публикует
набор модулей для внешних потребителей. Registry заменил бы понятные пути
обращениями через `config.flake.modules` без сокращения существенной логики.
Сохранены обычные imports. [Назначение модуля](https://flake.parts/options/flake-parts-modules).

## 6. Внедрённые инструменты

- Единый treefmt через **существующий** `pkgs.treefmt.withConfig`: nixfmt для Nix,
  shfmt для Shell и `.envrc`, Prettier для Markdown/YAML/JSON, Taplo для TOML.
  `nix fmt -- <files>` форматирует выбранные файлы, инструменты доступны в `nix develop`.
  Использован [стандартный интерфейс Nixpkgs](https://nixos.org/manual/nixpkgs/stable/#treefmt).
- `check.sh static --base REF` проверяет формат изменённых файлов на временных
  копиях, отслеживаемый diff на пробелы/конфликтные маркеры, ShellCheck и Python-тесты.
  Ошибки перечисления файлов останавливают проверку. Дерево и Git index сохраняются.
- `packages.x86_64-linux.dev-ports-test`: отдельный NixOS VM test для собственного
  firewall-модуля. Два гостя по 512 MiB, два изолированных интерфейса, настоящий
  HTTP-сервис, проверка разрешённого и запрещённого TCP-доступа.
- Команда `flake-check` из devenv запускает инструменты основного locked flake.

Полное форматирование старых файлов не выполнялось. В исходном дереве были
семь Nix-файлов, не проходящих текущий nixfmt; массовое исправление не относится
к архитектурной задаче. Форматируется и проверяется изменённая часть.

## 7. Отложенные технологии

| Технология                            | Решение и причина                                                                                                                                                                                   |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| treefmt-nix                           | Новый input не нужен: закреплённый Nixpkgs уже предоставляет нужную обёртку.                                                                                                                        |
| git-hooks.nix                         | Быстрые проверки доступны одной командой. Автоматическая установка меняет локальную конфигурацию hooks; дополнительный слой не требуется. Существующий input в независимом devenv не активировался. |
| sops-nix                              | Нет активного зашифрованного service-secret с согласованными ключами и восстановлением. Начальные пароли требуют отдельной миграции доступа, описанной ниже.                                        |
| Disko / nixos-anywhere                | Есть три существующих аппаратных конфигурации; сценарий новой или массовой установки не задан. Разметка и загрузчики сохранены.                                                                     |
| Новый Cachix / Attic / remote builder | Измерения не обосновывают дополнительную инфраструктуру и доверенные ключи.                                                                                                                         |
| Dendritic / module registry           | Не добавляют пользы для текущих явных imports.                                                                                                                                                      |

Проверен [установщик закреплённого git-hooks.nix](https://github.com/cachix/git-hooks.nix/blob/43b3c1ab9d40fb1dbb008f451988a91e375825e9/modules/pre-commit.nix):
его автоматическое применение не соответствует цели сохранить пользовательские
hooks. Git hooks и `core.hooksPath` в этой работе не менялись.

## 8. Управление хостами

Сохранены NixOS outputs `desktop`, `laptop`, `noop`; Home Manager `zerokqx`,
`noop` и алиас `zerok`. Новый хост требует собственного hardware-файла,
явных imports в своём модуле, записи `nixosSystem` в реестре и ожиданий в тесте.

Встроенный `noop` по-прежнему объединяет два HM-профиля. Сравнение обнаружило
изменение порядка списков при первоначальном переносе imports. Исправление —
обычный inline NixOS module после `personal.nix`; отдельный helper и изменение
приоритетов не понадобились. После исправления вернулась исходная derivation.

Hardware, диски, загрузчик, `stateVersion`, SSH, пользователи, сеть и поведение
служб сохранены. `rebuild.sh` по умолчанию только собирает; activation остаётся
отдельной явно выбранной операцией.

## 9. Binary caches и доставка пакетов

Сохранены cache.nixos.org, hyprland.cachix.org и ryoppippi.cachix.org с прежними
ключами. Все три `nix-cache-info` ответили HTTP 200, `StoreDir: /nix/store`;
приоритеты 40/41/41. У 3618 из 4437 уникальных путей трёх систем в локальном
store зарегистрирована подпись `cache.nixos.org-1`, у остальных подписей нет.
Это данные локального store, а не процент попаданий в кеш.

Выборочные HTTP GET к восьми `.narinfo` показали:

| Hyprland 0.55.3                                                                     | 200             | 404                     |
| Codex 0.166.0                                                                       | 200             | 404                     |

Это доступность конкретных путей на момент аудита. Полный hit rate, сетевой
трафик чистой установки и время холодной сборки не измерялись. Store не очищался.
Отдельные Nixpkgs/overlays upstream сохранены: их объединение могло бы изменить
пакеты и доступность substitutes. Подписи и sandbox не отключались.

| Closure          | Пути | NAR, байты до и после |
| ---------------- | ---: | --------------------: |
| desktop          | 4347 |        45 013 707 008 |
| laptop           | 4195 |        42 652 923 368 |
| noop             | 4192 |        42 637 453 728 |

Получателю с точным desktop closure недостаёт 48 путей/99 256 184 NAR bytes для
laptop либо 54 путей/77 818 616 bytes для noop. Это объём до сжатия/substitutes,
не реальный сетевой трафик. Поэтому предпочтительна передача недостающих путей
через [nix copy](https://nix.dev/manual/nix/2.34/command-ref/new-cli/nix3-copy.html),
а не архивирование всего store.

Настроенных remote builders нет. `builders-use-substitutes` само их не создаёт.
Автоматическая оптимизация при добавлении путей и периодическая дедупликация,
еженедельный GC, trusted users и package policy сохранены. Удаление дублирующего
штатный NixOS cache объявления и изменение расписаний отложены: выигрыша не
измерено. [Правила substitutes](https://nix.dev/manual/nix/2.34/command-ref/conf-file.html#conf-substituters).

Работающий daemon ещё использует настройки до первой итерации, включая старый
некорректный `cachix.org`. Репозиторий уже исправлен, но activation не выполнялась.
Для отдельных проверочных сборок CLI ограничивал substituters тремя настроенными
доверенными кешами, `max-jobs=2`, `cores=2`; системные настройки не менялись.

## 13. Оставшиеся риски и границы проверки

- В `core/users/` остаются plaintext `initialPassword` для привилегированных
  пользователей; NixOS переносит их в `users-groups.json` в store. SSH разрешает
  парольный вход. Это **не устранённая** проблема существующей конфигурации,
  поэтому полное соблюдение требования об отсутствии secrets в store не заявляется.
  Реальные действующие пароли не проверялись. Изменение доступа требует отдельного
  разрешения и проверенного резервного входа.
- `home/zerokqx/git.nix` использует `credential.helper = store`. Наличие реальных
  HTTPS credentials не проверялось; возможное plaintext хранение остаётся риском.
- Исторические файлы `certs/` имели заголовки git-crypt и удалены из текущего дерева;
  `d.txt` пуст. Сборка разблокированного checkout может включить plaintext в Nix
  source/store. Backup devenv также архивирует рабочее дерево. Процедура безопасного
  хранения и восстановления описана в [operations.md](operations.md#секреты-и-восстановление-доступа).
- Сохранилось исходное предупреждение Home Manager о `nixpkgs.overlays` вместе с
  `useGlobalPkgs` от закреплённых Stylix-модулей. Его исправление требует отдельного
  решения по владению package set, а не подавления предупреждения.
- `devenv.lock` остаётся отдельным rolling окружением. Проверки проекта используют
  основной `nix develop`; полного объединения двух сред не выполнялось.
- Совпадение derivations и успешная сборка не являются новым тестом загрузки
  физических desktop/laptop/noop, устройств, fingerprint, GPU или реального SSH.
  Switch/boot/test activation, reboot, deployment, ротация, GC и disk operations
  не выполнялись.

## 14. Следующие шаги

1. Отдельно согласовать устранение начальных паролей после проверки консоли или
   второго входа. Использовать root-only runtime `hashedPasswordFile`; sops-nix
   оправдан после выбора ключей и процедуры восстановления, например
   [neededForUsers](https://github.com/Mic92/sops-nix#setting-a-users-password).
2. Определить подходящий credential helper и проверить последствия перехода
   отдельно от архитектурной миграции.
3. Решить предупреждение Stylix/HM при следующем согласованном обновлении inputs.
4. Собирать данные о реальных cache misses перед добавлением builder/cache server.
   Не интерпретировать уменьшение lock-графа как доказанное ускорение сборки.
5. При появлении конкретной новой машины оценить Disko/nixos-anywhere и добавить
   только её декларативную схему и тесты; не менять существующие диски автоматически.
