# Архитектура ZNix

ZNix использует Flakes, NixOS modules и встроенный Home Manager. Версии задаёт
`flake.lock`; рефакторинг не обновляет зависимости. Архитектура рассчитана на
явное подключение возможностей через стандартные `imports`, без собственного
языка ролей и автоматического обнаружения каталогов.

## Решение и границы миграции

Исходный checkpoint — `faead27`. В `20c0da4` исправлены ссылки на перемещённый
Codex-модуль и удалённые пользователем файлы OBS/OpenCode. Этот исправленный
коммит служит базой сравнения; исходный checkpoint мог не проходить evaluation.

- `hosts/default.nix` становится явным реестром NixOS и standalone Home Manager.
  Каталог с `default.nix` сам по себе больше не создаёт публичный output.
- `hosts/<name>/default.nix` — обычный NixOS-модуль. Аппаратные настройки,
  мониторы, swap и настройки конкретной машины остаются здесь.
- `lib/` содержит только общие конструкторы систем и Home Manager, общий список
  внешних Home Manager modules и единую политику пакетов.
- `configuration.nix` отвечает за базовую композицию системы. `profiles/`
  собирает рабочее место, разработку и personal (пользователи, VPN и HM). Это обычные
  NixOS-модули, подключаемые путями, а не ещё одна система опций или ролей.
- `core/` и `configs/` сохраняют действующие предметные модули. Перемещение всех
  файлов в новый каталог `modules/` не решает самостоятельной задачи.
- `home/zerokqx/` и `home/noop/` сохраняют пользовательские настройки.
  Встроенный `noop` исторически объединяет оба профиля, standalone `noop` —
  только свой. Эта разница сохраняется явно для совместимости.
- `pkgs/` содержит сборку Rust-меню с ограниченным набором исходных файлов.
  Его сценарий установки должен регистрировать новые машины явно.
- `.agents/skills/` — единственный источник проектных skills. `AGENTS.md`
  служит короткой точкой входа; установка не меняет глобальные настройки агента.

## Сохраняемые контракты

| Output | Системное имя | Архитектура |
| --- | --- | --- |
| `nixosConfigurations.desktop` | `nixos-pc` | `x86_64-linux` |
| `nixosConfigurations.laptop` | `nixos-laptop` | `x86_64-linux` |
| `nixosConfigurations.noop` | `nixos` | `x86_64-linux` |

Standalone Home Manager: `zerokqx`, `noop`, алиас `zerok` → `zerokqx`.
Пакеты и приложения: `nixvim`, `menu`, `default` → `nixvim`.
Сохраняются `stateVersion`, загрузчик, диски, шифрование, доступ SSH,
сетевые настройки, пользовательские пакеты и действующие службы.

## Правила расширения

Новая машина получает свой аппаратный файл и обычный модуль, затем запись
в реестре с архитектурой и нужными профилями. Имя output и `networking.hostName`
могут различаться. Не копируйте UUID, resume offset и мониторы другой машины.

```nix
new-host = mkHost {
  system = "x86_64-linux";
  modules = [
    ../profiles/workstation.nix
    ../profiles/personal.nix
    ./new-host
  ];
};
```

`mkHost { system; modules; }` добавляет базовую конфигурацию и `inputs` в
`specialArgs`. Если hardware-модуль задаёт другую `nixpkgs.hostPlatform`,
evaluation останавливается с сообщением о несовпадении; без аппаратного
значения используется архитектура из реестра. `mkHome { system; module; }`
добавляет общую политику пакетов и внешние Home Manager-модули. Оба конструктора
находятся в `lib/default.nix` и не выполняют сборку или применение.

Для другого пользователя или серверного окружения выберите собственный обычный
модуль пользователей вместо `profiles/personal.nix`; он включает персональный
набор пользователя `zerok`. `workstation` импортирует `development`. Базовая
конфигурация сама не выбирает пользователя, VPN или графическое окружение.

Новый профиль нужен при повторном использовании связанного набора возможностей.
Одиночную настройку добавляйте в существующий профиль или модуль хоста.
Используйте `lib.mkDefault`, `lib.mkIf` и `lib.mkForce` непосредственно; не
создавайте обёрток над стандартными примитивами NixOS.

Новая CPU-архитектура требует проверки доступности всех выбранных пакетов
и flakes. Наличие параметра `system` не доказывает поддержку ARM существующим
рабочим окружением. Не включайте desktop-профиль в сервер без явного решения.

Rust-установщик автоматизирует создание и регистрацию x86_64-машины через
маркеры `znix-installer:hosts` и `znix-installer:homes`. Он проверяет платформу,
не заменяет существующие каталоги и блокирует параллельную запись реестра.
При прерванном процессе оставшийся `hosts/.znix-installer.lock` требует проверки
отсутствия другого установщика перед ручным удалением. Другие архитектуры
регистрируются явно после проверки совместимости.

## Порядок проверки

Проверка исходных файлов и формата → evaluation каждого output → проверки
контрактов → dry-build → сборка выбранных closures → отдельное разрешение
на активацию. Успешная evaluation не подтверждает загрузку или работу устройств.
Подробные команды и доставка пакетов описаны в [operations.md](operations.md),
результаты миграции — в [refactoring-report.md](refactoring-report.md).
